## Corrections to the originating design

Every claim below was checked against a primary source on 2026-09-04. These are recorded rather than quietly fixed, because several of them change what the plan should *do*.

### wrong — The docs page says PowerShell 7.7.0-preview.6 while releases show preview.4, proving docs/release desync.

**Correction.** Docs and Releases API agree at 7.7.0-preview.4. The "preview.6" is the .NET SDK version in the sentence "built on the .NET 11.0.100-preview.6 runtime" — a different axis, misread as the PowerShell version.

**Impact on the plan.** The conclusion survives and is strengthened: the real desync is PowerShell pinning SDK 11.0.100-preview.6 while .NET has shipped preview.7. But the verifier must model SDK and runtime as separate axes, which the original single-string design could not express.

`raw.githubusercontent.com/MicrosoftDocs/PowerShell-Docs/main/reference/docs-conceptual/whats-new/What-s-New-in-PowerShell-77.md`

### partially correct — PowerShell 7.7 should be the forward-looking track, implicitly becoming the next stable.

**Correction.** .NET 11 is STS (release-type "sts", 2 years support), not LTS. PowerShell inherits its support class from .NET, so the 7.7 line will never become the LTS track. 7.6 holds LTS until a PowerShell built on .NET 12.

**Impact on the plan.** Strongly validates the three-track design, and settles which track owns persistence: durable state follows LTS, never preview.

`builds.dotnet.microsoft.com/dotnet/release-metadata/releases-index.json`

### wrong — Hardcoding which PowerShell version is LTS is unavoidable.

**Correction.** PowerShell publishes master:tools/metadata.json with LTSReleaseTag as an array (currently ["v7.4.19","v7.6.5"]), plus Stable/Preview/Next release tags. First-party and machine-readable.

**Impact on the plan.** The verifier reads this instead of hardcoding. TRAP: aka.ms/pwsh-buildinfo-lts looks authoritative but returns v7.4.19 — it tracks an install channel, not LTS membership, and would be wrong by a full cycle.

`raw.githubusercontent.com/PowerShell/PowerShell/master/tools/metadata.json`

### partially correct — .NET 11 brings WASM improvements that make a real PowerShell-in-browser near.

**Correction.** Mono remains the Blazor/WASM runtime through .NET 11; CoreCLR-on-WASM is an opt-in early preview targeting stability in .NET 12. Separately, PowerShell has ZERO WASM support in-tree (RIDs are linux-x64;osx-x64). There is also no WASM multithreading in .NET 11.

**Impact on the plan.** RuntimeAdapter stays, and its value goes UP — but the .NET/WASM branch is a research spike, not a scheduled milestone. All concurrency must be browser-side (SharedWorker + Web Locks + OPFS), not .NET threads.

`devblogs.microsoft.com/dotnet/coreclr-progress-and-mono-timeline-dotnet-maui/ + dotnet/runtime#121511`

### partially correct — SharedWorker is unavailable on some modern browsers, so a dedicated-worker fallback is needed.

**Correction.** Chrome Android shipped SharedWorker in 148 (stable 2026-05-05); Safari has had it since 16.0 (not 16.4 — that is the OPFS milestone). MDN Baseline: "Newly available" since May 2026. But Samsung Internet and Opera Mobile still have none.

**Impact on the plan.** The Android-Chrome fallback branch is dead code. Keep a fallback anyway, for Samsung Internet and for the young Baseline floor.

`MDN browser-compat-data api/SharedWorker.json + developer.chrome.com/release-notes/148`

### confirmed with caveat — A SharedWorker can act as the storage coordination hub.

**Correction.** It can coordinate, but it can never hold the files. The WHATWG spec marks createSyncAccessHandle [Exposed=DedicatedWorker], which excludes both Window AND SharedWorker.

**Impact on the plan.** Confirms the split already in the design: SharedWorker elects and coordinates, a dedicated StorageWorker owns sync handles. Worth stating as a hard constraint so nobody "simplifies" it later.

`fs.spec.whatwg.org/#filesystemfilehandle`

### wrong — The PowerShell team maintains an MCP server to integrate against.

**Correction.** The 2026 investments post commits to building one ("we plan to develop a team supported MCP server"), with security as the initial focus. No such repo exists in github.com/PowerShell as of 2026-09-04; all existing PowerShell MCP servers are third-party. PowerShell/AIShell was archived 2026-01-30.

**Impact on the plan.** The MCP work must define its own tool schema from our command metadata. Do not plan to conform to an upstream schema that does not exist.

`GitHub org enumeration and code search across github.com/PowerShell (106 public repos, 0 matching mcp)`

### confirmed with caveat — PSReadLine 2026 roadmap items (context-aware prediction, input/render decoupling) justify designing for them now.

**Correction.** Both items are in the post verbatim, but both are exploratory — "We are exploring ways", and the decoupling is called "a fundamental change that will take time". PSReadLine is idle since 2026-04-08 (default branch master, not main) with no PR touching either.

**Impact on the plan.** Headless LineEditorCore is still right — it is good architecture on its own merits. But it must not be justified as "matching what upstream is shipping", because upstream is not shipping it.

`devblogs.microsoft.com/powershell/powershell-openssh-and-dsc-team-investments-for-2026/`

### partially correct — DSC v3.2 is the current release to model against.

**Correction.** DSC 3.2.0 GA'd 2026-04-29 with all four cited features (version pinning, --what-if, expression language with map/filter, adapters). But latest stable is v3.2.3 and v3.3.0-rc.2 shipped 2026-08-24.

**Impact on the plan.** Model the 3.2 feature set; pin the exact version in the profile rather than saying "3.2".

`api.github.com/repos/PowerShell/DSC/releases`

### partially correct — PSResourceGet supports OCI/ORAS registries.

**Correction.** OCI/ACR ships today; ORAS is explicitly future work — "we are working to adopt the .NET ORAS library", with 0 code hits for ORAS in the repo. MAR-as-trusted-source, explicit trust config, concurrent install and discovery/consumption separation are all confirmed. 1.3.0-preview1 is real (2026-05-20); latest stable is 1.2.0.

**Impact on the plan.** Model the trust/promotion pipeline, which is the actually-shipped idea. Do not claim ORAS.

`devblogs.microsoft.com/powershell/powershell-psresource-roadmap-and-best-practices/`

### partially correct — Use the wharflab/tree-sitter-powershell grammar as the PowerShell syntax front end.

**Correction.** That repo is real and MIT, but it is 5 months old with 2 stars and a commit history of Renovate bumps. The established grammar is airbus-cert/tree-sitter-powershell (85 stars, MIT), which is what nvim-treesitter actually pins; wharflab is a detached derivative of it. PowerShell/tree-sitter-PowerShell has been archived since 2024-01-09.

**Impact on the plan.** Point the syntax spike at airbus-cert. All the claimed grammar features were verified present in its derivative, so the capability argument holds either way.

`api.github.com/repos/{wharflab,airbus-cert}/tree-sitter-powershell + nvim-treesitter parser pins`

### wrong — VS Code issue #328110 proves tree-sitter parse success cannot be trusted as a safety boundary.

**Correction.** It shows the opposite. #328110 documents fail-CLOSED behaviour: an unparsable command resolves to noMatch and the user gets a confirmation prompt. Its 8% also rests on a hand-picked n=36. The argument needs microsoft/vscode#294010 (closed 2026-04-16), where "--flag=value" parses SUCCESSFULLY but wrongly as an assignment and truncates the command.

**Impact on the plan.** The design conclusion survives and is arguably stronger — a confident wrong parse is worse than a refused one — but the citation must be corrected or the argument collapses under review.

`github.com/microsoft/vscode/issues/328110 and /294010`

### wrong — ZenFS is LGPL-3.0 and therefore conflicts with this MIT repo.

**Correction.** The licence is LGPL-3.0-or-later, but the repo ships a supplemental grant in COPYING.md that expressly waives section 4(d) for software accessed over a network, i.e. exactly a web app. LGPL is weak copyleft designed to be linked from differently-licensed code. ZenFS was also plain MIT through 2.3.x (relicensed at 2.4.0, 2025-09-01).

**Impact on the plan.** Keeping FileSystemPort independent of any vendor stays good architecture, but it must not be justified by a licence conflict that does not exist. If ZenFS is ever adopted, the obligation is to offer the library Corresponding Source.

`github.com/zen-fs/core/blob/main/COPYING.md`

### partially correct — Vitest 5 requires Node >= 22.12.

**Correction.** Its engines field is ^22.12.0 || ^24.0.0 || >=26.0.0, which EXCLUDES Node 23 and Node 25. A plain >=22.12 hides that. Vitest 5.0.0 did ship 2026-09-03 as claimed. Vite is at 8.2.2, not 8.1.

**Impact on the plan.** Pin the CI Node version to an even-numbered line; an odd-numbered one silently fails to install.

`registry.npmjs.org/vitest and /vite`

### partially correct — Advanced runtimes must be hosted off GitHub Pages because it cannot set COOP/COEP headers.

**Correction.** Pages genuinely cannot set those headers, and the 1 GB site and 100 GB/month bandwidth limits are exact. But cross-origin isolation is achievable there via a same-origin service worker that synthesises the headers (coi-serviceworker), at the cost of one extra reload on first visit.

**Impact on the plan.** A separate lab origin is a tradeoff to choose, not a constraint to obey. Large VM and model assets still must not sit in the Pages artifact.

`docs.github.com/pages limits + github.com/gzuidhof/coi-serviceworker`

### partially correct — WebLLM verifies model artifact integrity.

**Correction.** The verification code is real (src/integrity.ts, SRI hashes) but OPT-IN: the field is an optional ModelIntegrity on the model record, and nothing is checked unless hashes are supplied. Realistic cold download for the smallest conversationally useful model is roughly 290-700 MB, which is separate from the vram_required_MB figure the docs list.

**Impact on the plan.** If AI is ever enabled, this project must supply the hashes itself and state the download size before starting it.

`github.com/mlc-ai/web-llm/blob/main/src/integrity.ts`
