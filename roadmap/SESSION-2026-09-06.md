### `feat/providers` — PR-10 tasks 1 and 2

Built: `src/providers/{types,registry,filesystem,session-state,index}.ts`, a
capability-layered interface (drive / item / container / navigation / content)
that is deliberately **not** `StorageBackend`, one `SessionStateProvider` for all
four session-state drives, and a `FileSystemProvider` adapting the brokered
`FileSystemPort`. `Get-ChildItem`, `Get-Content`, `Set-Location`, `Test-Path` and
`Get-Location` are rewired. `resolvePath` is still the only resolver.

Not done, and why:

- **Task 3** — the `Portfolio:`, `Process:`, `Package:` and `Browser:` providers.
  `providers/index.ts` states what adding one takes; `Set-Location Portfolio:/`
  reportedly needs only `isContainer`, because `canEnter` already routes it.
- **`IPropertyCmdletProvider`** is absent on purpose. Registry values are item
  properties, not child items — measured — so the layer is real, but building it
  with zero implementations would be the "declared but not implemented"
  dishonesty this repo tracks. The stream reports verifying that adding it later
  is a pure addition.
- No `New-PSDrive`, no dynamic parameters, and no `Get-Item` command — **that
  command does not exist in this repository at all**.
- **`Variable:` and `Function:` list nothing**, because this engine has neither
  variables nor user functions. Faithful to the engine, but a user typing
  `Get-ChildItem Variable:` sees an empty drive where pwsh shows ~40 automatic
  variables. **Not** recorded in `known-differences.yml`; the stream suggests it
  should be.
- `ls`, `cat`, `grep` and `tree` still go straight to storage, so from `Env:/`
  they answer `'Env:' is not a filesystem drive` rather than what pwsh does.
- The `unknown-drive` mapping parses the drive name back out of the resolver's
  message with a regex. Pinned end-to-end by a fixture test, but it couples three
  producers to one parser and the stream was not happy with it.
- Only the final tree was gate-verified; intermediate commits were not.

Two measurements in this session's own briefing were **wrong**, and the stream
corrected them:

- `formatResolved`'s comment claimed pwsh renders a provider drive with
  backslashes "on every platform". That came from a Windows-only measurement. In
  `pwsh-linux:7.6.5`, `Get-Location` inside `Env:` is **`Env:/`** and
  `ItemSeparator` is `/`. The emulated machine is Ubuntu, so the rendering was
  changed to `/`.
- Error messages do **not** always echo the path as typed. `-Path` normalises
  (`Env:\NoSuchVar`); only `Set-Location` and `-LiteralPath` echo it verbatim.

### `fix/kernelparse` — kernel runs the parser, format crosses the wire, AST limits

The kernel now calls `parseForExecution`; `splitPipeline` and `splitTokens` are
gone and `KNOWN_SURVIVORS` is empty. `FormatDocument` crosses the wire.
`engineLimits.unimplementedAstNodes` is derived rather than typed.

The independent review found the branch's own derivation was wrong in three
places and fixed them — the published node list is **40**, not the 37 the branch
shipped and not the 22 this session's briefing claimed:

- `VariableExpressionAst` is refused in code rather than via a table, so a
  derivation "from the three tables" could never see it.
- `CommandAst` was published as **unimplemented**, though every command the
  engine runs is one. The claim that the list and the behaviour could not
  disagree was false: it derived from message names, not from refusals.

Not settled:

- `$x [int]` and `$x (1)` are `UnexpectedToken` in pwsh but come back named
  `TypeExpressionAst` / `ParenExpressionAst`. These are refusals with a name one
  step too generous, not things that wrongly run. Fixing it means deciding which
  of ~40 token kinds continue an expression, which this parser deliberately does
  not answer.
- Refusal volume is uncapped on purpose, because pwsh reports every parse error
  with no cap. Measured: 64 KiB of `$a;` yields 21,845 refusals and 6.6M
  characters in one `rejected` event. It clones in 23 ms, so it crosses; a host
  rendering one line per problem is what will suffer.
- The wire ceiling is exactly **4,194,152 JSON characters** — 4,194,153 is
  refused. That is 148 below what the string charge alone allows, because the
  record's own type names and property name are charged first, so an assertion
  computed from the formula agrees with the wrong number.
