A frozen copy of the single-file terminal that this project is being rewritten
from - the same document as `index.html`, byte for byte apart from line endings
(see *Verifying this archive*). It exists so the rewrite has something to be
*correct against*: before this archive, `index.html` was the only specification
of how the site behaves, and a specification you are actively editing is not one.

Do not edit this file. If it needs to change, the archive is wrong.

## What it is

One HTML file: markup and CSS in lines 1-197, and a single `<script>` block
containing the entire engine. It implements 67 commands, 46 aliases and 11
easter eggs over a virtual Unix filesystem persisted to `localStorage`, with a
nano/vim editor, tab completion, prediction, themes, and full IME support.

It has no build step and no dependencies, which is why it has survived.

## Why it is being replaced

Not because it is bad — it is dense, careful work. Because it has no seams:
four independent tokenizers, commands that write directly to the DOM, a
filesystem layer that returns rendered view objects, and no object model, so
`gci | Sort-Object` sorts formatted text including the `UnixMode` prefix
rather than sorting objects by a property.

## Verifying this archive

Compare the content **after folding CRLF to LF**. Not the raw bytes, and — this
is the correction — not the git blob hash either.

Against `index.html` **at the archived commit**, not at `HEAD`. The archive is
frozen and the page is not: comparing with `HEAD` made this command — and the
test below — fail the first time the page was edited for any reason, which
happened on a routine refresh of the contribution counts.

```sh
c=0838080474d7e34d45cff9f242d2cdb7adde3380
a=$(git show "$c":index.html                 | tr -d '\r' | sha256sum)
b=$(git show HEAD:legacy/terminal-v1.html    | tr -d '\r' | sha256sum)
[ "$a" = "$b" ] && echo identical
```

Both are `dc9570a7…`, which is the row above.

`tests/unit/v1-transcripts.test.mts` asserts exactly this, against the same
commit, and a second test asserts that commit is still the one recorded here —
so the constant in the test cannot become a different claim from this document.
What it catches is the archive being edited after the fact, which is the thing
worth catching; what it deliberately no longer catches is the living page moving
on, which is not drift but the point of having an archive.

### Why not the git blob hash

An earlier version of this file said to compare `git hash-object` output and
claimed both files hashed to `21794ce2…`. That was written from the general rule
about `core.autocrlf`, not from a measurement, and the measurement refutes it:

```
$ git ls-files -s index.html legacy/terminal-v1.html
100644 21794ce2250e2ec525eb146fcd688e93407ea90d 0   index.html
100644 234cdfda9c4f5990da61190c3d47e2d1354c8e93 0   legacy/terminal-v1.html
```

The blob hash is normalised on check-in only for files git treats as text, and
`.gitattributes` declares **both** of these `-text` on purpose:

```
index.html -text
legacy/*.html -text
```

`index.html` is the deployed artifact and must never be rewritten by a checkout;
the archive is `-text` so it keeps the exact bytes it was taken with. The
consequence is that each file's blob is whatever its working tree held when it
was added — LF for `index.html`, CRLF for the archive, taken on Windows — and no
normalisation ever happens. So the two blobs differ, permanently, on a pair of
files that are the same document.

That is not a defect to fix by rewriting the archive. Keeping its original bytes
is the point of an archive, and `tools/check-source-bytes.mts` already knows
about the `-text` exemption. What was wrong was the sentence claiming a hash
equality that had never held.

The live site still serves `index.html`. This copy is the reference the
conformance suite replays against, and `index.html` is only replaced once that
suite reaches parity.
